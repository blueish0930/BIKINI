0. 一句话目标
--------------

把 michal1000w/blender-SCycles 的 Cycles 引擎整棵换进来，
丢掉自己现在的 SPPM 光子焦散。

要他的全部 Cycles 功能:
  - Progressive Photon Mapping（表面 + 体积焦散）
  - Bidirectional Path Tracing（含 surface→volume→surface 双向焦散）
  - GPU Path Guiding（他现在是 Metal 实现）
  - Pixel Displacement
  - Spectral transmission / 色散
  - Fast Volume、体积运动模糊相关、BDPT light tree
  - 反向 MNEE 接 BDPT

他的实现目前几乎全部锁在 Metal（macOS）里。Windows 上必须把同一套内核
接到 CUDA 和 OptiX，而不是再发明一套 SPPM。

BIKINI 里和 Cycles 无关的东西全部保留:
  LuxCore、DLSS、CGAL/Jolt/PMP/InstantMeshes、shader wrangle、
  ddx/ddy、节点工具、合成器扩展等。

1.4 为什么不能“直接编译他的分支”

  intern/cycles/kernel/device/gpu/kernel.h 里，下列全部包在
  #ifdef __KERNEL_METAL__ 里面:

    #include photon_mapping.h
    #include bidirectional.h
    #include guiding_gpu.h
    #include pixel_displacement_shader.h
    kernel integrator_photon_emit
    kernel integrator_bdpt_light_generate
    kernel integrator_bdpt_cache_order
    kernel integrator_bdpt_sensor_connect
    kernel guiding_begin_update / refine / publish / partition_* / fit / flush_history

  shade_surface.h 里:
    photon_mapping_gather()           只在 __KERNEL_METAL__
    integrate_surface_bidirectional() 只在 __KERNEL_METAL__
    GPU guiding bounce 记录           只在 __KERNEL_METAL__

  properties.py 原文:
    "Use progressive photon density estimates ... (Metal GPU only)"

  所以: 把 intern/cycles 换成他的之后，Windows CUDA 构建能编过，
  但光子图 / BDPT / GPU Guiding / Pixel Displacement 在 CUDA 上
  等于没接上，界面开了也不工作。适配 Windows 是本方案的主工程。

  更关键的一层: 就算把门控打开、CUDA 软件 BVH 能出图，
  默认 RTX 走的是 OptiX。MetalRT 允许从 compute shader 里求交，
  OptiX 的 optixTrace 只能从 OptiX pipeline（raygen 等）里调用。
  他的 integrator_photon_emit / integrator_bdpt_light_generate
  内部都调 scene_intersect。在 OptiX 设备上把它们当 cuLaunchKernel
  的普通 CUDA kernel 发射，求交会编不过或运行期非法。
  详见 7.4 和 7.7。


2. 明确的取舍（写进方案，避免做到一半改主意）
----------------------------------------------

要:
  SCycles 的整套 Cycles（光子图 + BDPT + GPU guiding + pixel displacement
  + spectral + fast volume + light tree for bidir + 反向 MNEE）
  在 Windows 上跑 CUDA，OptiX 硬件求交照常用

不要:
  自己的 SPPM（photon_map / photon_trace / photon_passes / hitpoint film）
  两套焦散同时开
  把 SCycles 整仓 merge 进 BIKINI
  第一期就做 HIP / oneAPI（CUDA/OptiX 稳定后再说）

保留:
  DLSS
  LuxCore
  BIKINI 所有非 Cycles intern 和编辑器功能

互斥策略（实现时写进 integrator）:
  use_photon_mapping 和 use_bidirectional_path_tracing 可以按他原设计共存
  （他已经用 MIS 划分，photon 替换 PT 采不好的那类，BDPT 另算策略）
  不再存在 use_photon_caustics（BIKINI SPPM 开关删除）

死路 C: 只 checkout 几个 .h，手改 shade_surface
  漏掉 DeviceKernel、path_trace_work_gpu 分配、Metal 管线、测试，必烂。

正路:

  1) 新分支 feature/scycles-windows
  2) 用 git checkout scycles/main -- intern/cycles
     整目录换成他的 Cycles
  3) 立刻把 DLSS 文件从旧提交拣回来，CMake 接回去
  4) 再 checkout 他 intern/cycles 之外、Cycles 功能真正需要的少数文件
     （volume_fast 节点、测试、OSL）
  5) 做 Metal → CUDA/OptiX 适配（本方案第 7 节，工作量最大）
  6) Windows 编过、焦散/BDPT/位移/体积场景过完，再考虑追官方

    DEVICE_KERNEL_NUM 和 CUDA kernel 表不一致（SCycles 加了 kernel 枚举）
    CMake 还引用已删的 photon_map.cpp


7. 阶段 6–8: Metal → Windows CUDA/OptiX（主工程）
-------------------------------------------------

这是本方案真正的开发，不是 git 操作。

7.1 适配原则（写死，避免改到一半乱）

  P1. 算法文件（photon_mapping.h, bidirectional.h, guiding_gpu.h）尽量不改逻辑。
      只改门控宏和少量后端原语。

  P2. 门控从
        #ifdef __KERNEL_METAL__
      扩成
        #if defined(__KERNEL_METAL__) || defined(__KERNEL_CUDA__) || defined(__KERNEL_OPTIX__)
      更好的做法是引入一个功能宏，避免每个文件复制三套:

        #if defined(__KERNEL_METAL__) || defined(__KERNEL_CUDA__) || defined(__KERNEL_OPTIX__)
        #  define __SCYCLES_GPU_TRANSPORT__
        #endif

      然后算法 include 和 shade_surface 调用都看 __SCYCLES_GPU_TRANSPORT__。
      Metal 专用的编译器/archive/纹理 cache miss 仍留 __KERNEL_METAL__。

  P3. Metal 独有、CUDA 没有对等物的，做空实现或跳过，不要假装:

        Metal 纹理 streaming / SR_CACHE_MISS / bdpt_surface_stage 重试
          → CUDA 上 shader 一次求完，cache miss 路径应恒为 false
        Metal 编译器异步 archive
          → CUDA 走现有 nvcc/OptiX module
        context.launch_params_metal
          → CUDA 用 KernelGlobals / kernel_integrator_state
        guiding_mixture_fit_metal.h
          → 优先改用 guiding_mixture_fit.h 的通用路径；
            Metal 特化只在 __KERNEL_METAL__ 保留

  P4. 第一期只保证:
        CUDA + OptiX，单 GPU
        光子图 gather + emit
        BDPT light cache + camera connect + sensor connect
        Pixel displacement 求值
      GPU Guiding 训练可以第二期，先让 CPU OpenPGL 在 CPU 设备上继续工作。

  P5. 寄存器/编译内存爆了，就学 Metal 把 kernel 拆模块，
      不要第一天就把 photon+bdpt+guiding+shade 打进一个 CUDA megakernel。

  P6. 分两步验证后端，不要一上来就 OptiX:
      第一步: Cycles 设备选 CUDA（软件 BVH），证明算法和调度
      第二步: 给 photon_emit / bdpt_light_generate 做 OptiX raygen
              （等价于你旧 SPPM 的 PIP_PHOTON）
      跳过第一步直接改 OptiX，分不清是算法错还是 pipeline 错。

7.4 CUDA 和 OptiX 的差异（v1.1 纠正）

  先分清两件事:
    A. 光子 gather / BDPT camera connect
       发生在已经存在的 shade_surface / shade_volume 里。
       OptiX 着色 module 打开 include 即可（仍在 OptiX pipeline 内，
       可以 optixTrace 阴影）。
    B. photon_emit / bdpt_light_generate
       是新的「从灯往外打」的核，内部循环调用 scene_intersect。
       Metal 上这是带 MetalRT 的 compute。
       CUDA 软件 BVH 上可以是普通 CUDA kernel。
       OptiX 上必须是 OptiX raygen，不能是 cuLaunchKernel。

  CUDA（软件 BVH，调试用）:
    intern/cycles/kernel/device/cuda/kernel.cu 包含 gpu/kernel.h
    门控打开后新 kernel 进同一个 module，scene_intersect 走 BVH2。
    风险: 编译时间、寄存器、Windows nvcc 内存。
    缓解: 只编本机 sm_XX；不要关 binaries 赌 Windows JIT（见 10.1）。

  OptiX（RTX 默认，产品路径）:
    optixTrace 只能从 OptiX device program 调用。
    官方文档: OptiX 是 MIMD 子集，禁止 threadgroup/shared 同步，
    warp ballot 的邻居线程不保证稳定。
    因此:
      1. intern/cycles/device/optix/queue.cpp 必须认识
         DEVICE_KERNEL_INTEGRATOR_PHOTON_EMIT 等新枚举，
         现在遇到未知 kernel 会 LOG_ERROR "Invalid kernel"
      2. 为 photon_emit、bdpt_light_generate 各做一条 raygen
         （照你旧 PIP_PHOTON 的拆法，或并进现有 pipeline 的新 entry）
      3. bdpt_cache_order 不含求交，可以留 CUDA compute
         （他已有单线程 #else，CUDA 先走这个，不要用 Metal warp 版）
      4. bdpt_sensor_connect 会 MNEE / 求交，按 OptiX raygen 处理
      5. shade 里的 photon_mapping_gather 只读哈希表，不求交，
         可留在现有 SHADE module
      6. 禁止在 OptiX 着色核里用 ccl_gpu_shared / __syncthreads
         做 BDPT 压缩；Metal threadgroup 那套不能搬
      7. OSL: OptiX 的 OSL module 没有 SVM。BDPT 重建 ShaderData
         走 surface_shader_eval<SVM>。OSL 材质第一期标不支持 BDPT/光子

  顺序:
    Day 4–5 强制设备 = CUDA（关掉 OptiX）把玻璃球打亮
    然后再接 OptiX raygen。UI 在 OptiX 未接完前，
    开光子/BDPT 时自动回退 CUDA 或弹错误，不要静默黑图。

  CPU:
    他的光子/BDPT 不是为 CPU 写的。Windows 上 CPU 保持官方 PT + OpenPGL。
    UI: 光子图/BDPT 仅 CUDA（软件 BVH 调试）和 OptiX（产品）。
    HIP 第一期灰掉。

7.5 原子、warp、对齐（CUDA 适配检查单）

  photon_store 用 atomic_fetch_and_add_uint32 / atomic_exchange_uint32
    → CUDA 已有，确认类型是 unsigned int，不要 size_t

  packed_normal、48 字节 KernelPhoton
    → 查 alignas / static_assert，CUDA 结构体对齐和 Metal 可能不同

  Spectrum 在光子记录里存成 float3

  kernel_integrator_state.photons 指针
    → path_trace_work_gpu::alloc 必须在 device 上分配，
      并写入 IntegratorStateGPU，和 Metal 同一布局

7.7 Mac Metal → Windows CUDA/OptiX：常见坑（审查补丁）
-------------------------------------------------------

下面都是「只开门控就能跑」这个幻想会踩到的。按杀伤力排序。

(1) OptiX 不能从普通 CUDA kernel 里 scene_intersect
    MetalRT: compute shader 可以求交。
    OptiX 7: optixTrace 只允许在 raygen / CH / AH / miss 等 pipeline 程序里。
    photon_mapping.h 的 integrator_photon_emit、bidirectional.h 的
    integrator_bdpt_light_generate 都是「自己 while 打射线」。
    产品默认 RTX + OptiX。这不是优化问题，是能不能合法运行。
    预案见 7.4。你旧 SPPM 已经做过独立 PIP_PHOTON，这段经验要复用，
    不要当成「SCycles 更现代所以不用 pipeline」。

(2) WDDM TDR（Windows 独有，Mac 没有这个 2 秒刀）
    默认 TdrDelay=2 秒。百万级 photon_emit 或 BDPT light generate
    一次 launch 超过 2 秒，驱动重置，blender 黑屏/设备丢失。
    Metal 统一内存上长时间 kernel 不会被 Windows TDR 砍。
    必须:
      - photon_emit / bdpt_light_generate 按容量切片 launch
        （例如每片 64k–256k paths，中间 queue->synchronize）
      - 开发机可以临时加 TdrDelay，产品不能要求用户改注册表
      - 视口里更要切片，否则一拖灯就 TDR

(3) CUDA __constant__ 只有 64KB: KernelParamsCUDA
    intern/cycles/kernel/device/cuda/globals.h:
      KernelParamsCUDA = KernelData + 全部 data_arrays 指针
                       + IntegratorStateGPU
    SCycles 往 IntegratorStateGPU 塞了:
      photons / photon_hash / photon_stored
      bdpt_vertices / indices / count
      一整排 guiding_* 指针
      以及 photon_radius、bdpt_buffer_* 等标量
    阶段 2 之后立刻在 host 和一份小 CUDA kernel 里
      printf("%zu\n", sizeof(KernelParamsCUDA));
      static_assert(sizeof(KernelParamsCUDA) <= 65536);
    超了的典型症状: cuMemcpyToSymbol 失败、内核读到垃圾指针、随机花屏。
    预案: 把光子/BDPT/guiding 的大指针块改成单独的 device 结构，
    只在 KernelParams 里留一个指针，不要无限加字段。

(4) IntegratorStateGPU 布局是按 Metal 抄的
    state.h 原文:
      "Metal photon-map working memory. These remain null on other devices"
      "Scalars must follow sort_partition_divisor: Metal translates
       the preceding pointer block."
    含义:
      a) checkout 之后 CUDA 上这些指针默认是 null，不开 alloc 就 gather 空
      b) Metal host 可能只拷贝「指针块」，标量另拷。CUDA 是整颗
         KernelParamsCUDA 一次 cuMemcpyToSymbol。
         必须保证 MSVC/clang-cl（host）和 nvcc（device）对
         IntegratorStateGPU 的 sizeof / offsetof 完全一致。
    检查:
      编译期 static_assert(sizeof(KernelPhoton)==48);
      static_assert(sizeof(KernelBDPTVertex)==112);
      打日志 offsetof(IntegratorStateGPU, photons) 等，host 与 device 对拍。
    这是 CUDA 移植第一经典坑: host 写了 radius，device 读到的是指针碎片。

(5) ShaderData 里 GPU Guiding 缓存只存在于 Metal
    types.h:
      #ifdef __KERNEL_METAL__
        const ccl_global float *gpu_guiding_weights;
        float3 gpu_guiding_cached_P;
        ... 大约十几个 extra 字段
      #endif
    如果为了「开门控」把 guiding_gpu.h 和 shade_surface 的 guiding 调用
    直接改成 CUDA，会：
      - 编译失败（没有这些成员），或
      - 你把字段加进 CUDA ShaderData，占用爆炸，occupancy 掉光
    结论: 第一期 CUDA 不要开 GPU Guiding。
    shade_surface 里 GPU guiding 记录继续 #ifdef __KERNEL_METAL__。
    光子 gather / BDPT connect 不要和 guiding 字段绑在一起。
    CPU 设备继续官方 OpenPGL。__PATH_GUIDING__ 在 features.h 里
    对 GPU 是关掉的，GPU guiding 是另一套 Metal 内核，不是 OpenPGL。

(6) Apple 的 packed integrator state 不会来救 CUDA
    __INTEGRATOR_GPU_PACKED_STATE__ 只在 Apple Silicon 打开。
    CUDA 一直是 SoA 数组。不要把 Metal packed accessor 抄到 CUDA。
    打开门控时，INTEGRATOR_STATE() 宏走的是 CUDA 的
      kernel_integrator_state.nested_struct.member[state]
    他 Metal 代码如果用了 member##_fn() packed 访问，CUDA 编不过。
    搜 member##_fn 和 packed_shadow_ray，确认算法头文件没用这些。

(7) warp / simdgroup / 共享内存
    Apple GPU simdgroup 通常 32，和 CUDA warp 一样，但:
      Metal: threadgroup 共享内存 + simdgroup 扫描，他用来做
             bdpt_cache_order、guiding partition
      CUDA compute: 可以 __shared__ + __ballot_sync，但
             ccl_gpu_ballot 写死了 mask=0xFFFFFFFF，发散 warp 会错
      OptiX: 禁止 shared/barrier；ballot 的「邻居」不保证是空间邻居
    所以 BDPT cache_order 在 CUDA/OptiX 第一期必须走他已经写好的
    单线程 #else（kernel.h 里非 Metal 分支）。
    不要把 Metal warp 版用 #ifdef __KERNEL_GPU__ 打开。

(8) 原子操作和哈希表
    photon_store: atomic_fetch_and_add 槽位 + atomic_exchange 链头
    CUDA 全局原子没问题（SM 6.0+，RTX 都满足）。
    坑在:
      - 槽满了静默丢光子（他已有 capacity 检查），Windows 上要打 host 计数
      - 很多线程打同一 hash bucket，原子争用比 Metal 更疼（NVIDIA 全局原子）
      - 必须 cudaDeviceSynchronize 或 queue sync 之后，camera gather
        才能看见完整链表。漏一次 sync 就是闪烁/缺块焦散
    Metal 统一内存在 CPU 侧有时看起来「马上可见」，CUDA 不会。

(9) 离散显存 vs 统一内存
    Mac: 光子数组 + BDPT 顶点 + guiding history(上限 4GB) 吃统一内存，
         超了还能换页，只是变慢。
    Windows NVIDIA: 超 VRAM 就是 cudaMalloc 失败，渲染死掉。
    必须:
      - alloc 失败要降 photon_capacity / bdpt_vertex_capacity，不要 abort
      - 8GB 卡默认光子/BDPT 预算写保守值（例如光子 2M、BDPT 顶点 1M）
      - 4GB guiding history 第一期不要暴露给 CUDA UI
      - 加上现有 path state（1080p 视口就很大），三套一起会 OOM

(10) SR_CACHE_MISS / 纹理流式 / bdpt_surface_stage
    Metal Cycles 有纹理 tile cache，miss 就 SR_CACHE_MISS，
    shade_surface 用 bdpt_surface_stage 0/1/2/3 避免重写 film。
    CUDA/OptiX 官方路径几乎不走这套（纹理常驻）。
    把门控打开后:
      CUDA 上 sd.runtime_flag 的 SR_CACHE_MISS 应恒为 0
      不要把 Metal 的「重试着色」状态机启用，否则 stage 卡死、重复连接
    无纹理玻璃先验收。复杂 Image Texture 玻璃第二期再对。

(11) 半精度 / 数学差异
    KernelPhoton 用 packed_normal、time_wavelength 的 16bit。
    CUDA packed_normal 已有，但 decode 精度和 Metal 可能差 1 ULP，
    焦散边缘可能有噪点差，不要当回归失败。
    Blender 自己修过 “Metal lgammaf 精度低于从前”。
    光谱波长 pack 15bit，带宽 0.02，两边应一致。

(12) 编译器组合
    Host: MSVC 或 clang-cl（你的树是 vc17）
    Device: nvcc / NVRTC
    结构体尾部 uint/float 混排，MSVC 和 nvcc 填充规则必须用
    static_assert_align 锁死。KernelPhoton / KernelBDPTVertex
    他已经 static_assert 48 和 112，IntegratorStateGPU 没有，要补。
    NVRTC JIT 第一次编 shade_volume+bidirectional 可能:
      - 临时目录路径太长（Windows MAX_PATH 260）
      - Defender 扫 .ptx 把编译拖到分钟级
    预案: 短构建路径（E:\b\ 而不是很长的 Grok 路径）、排除 Defender。

(13) 新 DeviceKernel 枚举必须贯穿整条 host 链
    types.h 已有:
      DEVICE_KERNEL_INTEGRATOR_PHOTON_EMIT
      DEVICE_KERNEL_INTEGRATOR_BDPT_LIGHT_GENERATE
      DEVICE_KERNEL_INTEGRATOR_BDPT_CACHE_ORDER
      DEVICE_KERNEL_INTEGRATOR_BDPT_SENSOR_CONNECT
      DEVICE_KERNEL_GUIDING_*
    checkout intern/cycles 后 device/kernel.cpp 的 as_string / has_shading
    应已带上。但仍要人工确认:
      device/cuda/kernel.cpp   cuModuleGetFunction("kernel_gpu_integrator_photon_emit")
      device/optix/queue.cpp   新 kernel 的 enqueue 分支（现在会 Invalid kernel）
      device/optix/device_impl.cpp  pipeline 创建
      IntegratorQueueCounter::num_queued[DEVICE_GPU_KERNEL_INTEGRATOR_NUM]
        数组长度是否含新 integrator kernel
    漏一个就是「编译过、按钮开了、永远不 launch」。

(14) 光子/BDPT 不是 queued path kernel
    它们不走 integrator_queued_paths_array。
    必须在 PathTraceWorkGPU 里显式:
      每 N 个 camera sample → launch photon_emit → sync → 之后 shade 才能 gather
      每 bdpt_update_samples → light_generate → cache_order → shade connect
    Metal 的 path_trace_work_gpu.cpp 已经写了这套。
    CUDA 设备判断如果写死 DEVICE_METAL，checkout 后 Windows 上
    alloc/launch 整段被跳过，指针保持 null（state.h 注释就是这么说的）。
    阶段 6 第一件事: 把 if (metal) alloc_photons 改成 if (gpu_transport)。

(15) KERNEL_FEATURE_BDPT / PHOTON_MAPPING 是 bit 32/33
    uint64_t 没问题。Metal 用 __KERNEL_METAL_TRANSPORT_FEATURES__
    按场景裁 pipeline，CUDA 默认一个大 kernel 会把两套代码都编进去。
    没开光子的普通 PT 也会吃寄存器。
    中期用 Cycles 已有的自适应编译（__KERNEL_FEATURES__）
    把未使用的 BDPT/光子从该场景的 kernel 里裁掉。

(16) 官方 MNEE 和 BDPT 反向 MNEE 抢状态
    他扩展了 mnee.h 的 kernel_path_mnee_sample 签名
    （wavelength、volume_vertex、manifold_vertices）。
    CUDA/OptiX 的 MNEE 模块必须用新签名，否则链接失败。
    阴影焦散物体标记 SD_OBJECT_CAUSTICS_* 仍是官方的。
    双向体积焦散还要求透视相机、没 shadow linking。
    验收时用透视，不要用正交/全景当第一张图。

(17) 取消渲染 / 设备重置
    Metal 异步 compiler 他专门修过 shutdown。
    CUDA: 取消时 queue->synchronize + 释放 photons/bdpt buffer。
    TDR 之后 device 指针全废，要走 Cycles 已有的 CUDA 错误恢复，
    不要假设 photon_hash 还活着。

(18) 多 GPU
    他 Metal 实现按单设备 cache。CUDA 多卡第一期关掉光子/BDPT
    （和你旧 SPPM 单 GPU 一样）。KernelPhoton.emitter_object 是

10. 构建命令（Windows 实操）——v1.2 按论坛经验改过
----------------------------------------------------

  官方手册:
    https://developer.blender.org/docs/handbook/building_blender/cycles_gpu_binaries/

  10.1 不要在 Windows 上赌运行时 JIT

    v1.0 写「WITH_CYCLES_CUDA_BINARIES=OFF，启动后再 nvcc」。
    这在 Linux/mac 还行，Windows 上被 LazyDodo 和无数帖子打脸:

      「on demand compilation on Windows: finding both a compatible
        cuda in the PATH and running from a compatible VS developer
        prompt — essentially never right」
      典型报错: nvcc fatal: Cannot find compiler 'cl.exe' in PATH
      make 出来的 exe 切 GPU 就炸；make release 因为预编了 cubin 才能用

    正确做法（开发机）:
      WITH_CYCLES_DEVICE_CUDA=ON
      WITH_CYCLES_DEVICE_OPTIX=ON
      WITH_CYCLES_CUDA_BINARIES=ON          ← 必须 ON
      CYCLES_CUDA_BINARIES_ARCH=sm_89       ← 只留你的卡，见下
      OPTIX_ROOT_DIR=你现在 BIKINI 已经在用的 SDK，不要换新
      WITH_COMPILER_ASAN=OFF                ← ASAN 会让 CUDA 初始化失败
      用 Release，不要用 Debug 编 GPU kernel

    迭代时不要关 binaries。nvcc 编一个 arch 虽然慢，但比「启动后找不到 cl.exe」
    可靠。真要 JIT 调试，必须从 “x64 Native Tools Command Prompt for VS”
    启动 blender.exe，且 nvcc 在 PATH。不要把 MSVC 14.xx.xxxxx 写死进系统 PATH
    （VS 一升级路径就废）。

  10.2 只编自己的架构，否则内存和耐心都会爆

    开发论坛共识: 全量 sm_50..sm_120 编 CUDA/OptiX 要很久，多线程 nvcc
    还容易把机器编崩。
    cmake-gui 搜 CYCLES_CUDA_BINARIES_ARCH，开发期只留一张卡:
      RTX 20 系  sm_75
      RTX 30 系  sm_86
      RTX 40 系  sm_89
      RTX 50 系  sm_120（CUDA 12.8+；CUDA 13 还可能踩 PTX 校验，见 10.4）
    compute_75 是给「没预编译的新卡」用的 PTX，开发机可删，省时间。
    多 arch 时若 RAM 不够: WITH_CYCLES_CUDA_BUILD_SERIAL=ON（串行编核）。
    CUDA 12.9+ 的 --split-compile 只在 arch 数量 ≤2 时官方才开，避免吃光内存。

    LazyDodo 开发习惯: 先 CPU（WITH_CYCLES_NATIVE_ONLY）把 host 逻辑写对，
    GPU binaries 最后再开。光子/BDPT 的 host 调度（path_trace_work_gpu）
    可以在 CPU 编不过的情况下先读代码，但功能验收必须 GPU。

  10.3 OptiX SDK 版本必须配驱动，不要追最新

    官方 handbook: OptiX SDK 8.0 or newer，先把 CUDA binaries 配好。
    论坛实锤: 自己编时用了 OptiX 9.1，驱动 576 被判定太旧
    （9.1 要求 R590+）；官方构建用 8.0，535+ 就行。
    同一台机器官方 blender OptiX 正常、自己编的报 driver too old，
    就是 SDK 比驱动新。
    本方案: 锁死你当前 BIKINI 能编过的 OPTIX_ROOT_DIR 和驱动，
    不要为了 SCycles 去装 9.x。
    驱动里的 libnvoptix 和 SDK 头文件不是同一份东西：
    编译只需要头文件，运行用驱动。头文件过新 = 运行期符号对不上。

  10.4 CUDA 13 / Blackwell / 运行时编 OptiX PTX

    projects.blender.org #152789 (Patrick Mours, 2026-01):
      CUDA 13 + Hopper/Blackwell 目标时，nvcc 会做 PTX verification，
      解析不了 OptiX device intrinsic，运行时编 OptiX kernel 失败。
      官方 workaround: PTX 目标不要超过 compute_89。
    #152417: CUDA 13 直接不认 compute_50，main 编不过。
    若本机是 CUDA 13: 确认 intern/cycles 已含上述修复；
    没有就不要用 CUDA 13 编 OptiX，退回 12.x。

  10.5 内核缓存，改 intern/cycles 之后必清

    Windows:
      %APPDATA%\Blender Foundation\Blender\5.3\cache\kernels\
      %LOCALAPPDATA%\NVIDIA\OptixCache\
    官方 blender 换驱动/改核后「Illegal address」「OPTIX_ERROR_INTERNAL_COMPILER_ERROR」
    第一反应就是删这两个目录。
    你每天改 photon_mapping.h / bidirectional.h，旧 cubin/ptx 哈希对不上
    或更糟：哈希碰巧撞上，加载到半旧内核。
    阶段 2 换完 intern/cycles、每次大改 kernel 头文件之后都清。

    macOS 对照（你不编 Mac，但知道差异）:
      Metal 内核运行时编，cmake 不用 binaries
      缓存: ~/.cache/cycles 以及 `getconf DARWIN_USER_CACHE_DIR`
            下的 org.blenderfoundation.blender、com.apple.metal
      5.0 上 Metal 首编从 ~20s 变成 ~210s（#150119）。
      SCycles 又拆了更多 pipeline，Mac 上会更慢；Windows 预编译
      把这笔账付在 cmake 阶段，启动时不应再编（除非缺 arch）。

  10.6 OptiX 二次编核、栈溢出、花屏

    AO / Bevel / 官方阴影焦散 会触发独立的 shader_raytrace OptiX module，
    首次「Loading render kernels」能卡几分钟，看起来像死机。
    论坛: 让它跑完，中途取消更容易真卡死。
    你加上 BDPT/光子之后，这个 module 会更肥。

    projects #150085 本地 OptiX 编出来:
      Continuation stack allocation too large
      OPTIX_ERROR_INTERNAL_COMPILER_ERROR
    原因: raygen 里 trace 次数 + 指令数爆了（MNEE + 巨大 shade）。
    把 bidirectional.h 塞进 SHADE 而不拆 pipeline，Windows 上
    很可能会打到这个错误，Mac Metal 没有「continuation stack」这个概念。
    预案: 光子 emit / BDPT generate 独立 raygen（7.4）；
          shade 里 gather 尽量 inline 小；MNEE+BDPT 不要和 AO 节点同一张
          首测图。

    Illegal address in CUDA queue copy_from_device
    常见于: 内核与 host 结构不一致、VRAM 碎了、并发 path state 太多。
    4090 比 3090 更容易报 OOM 的怪帖（#109025）:
      设环境变量 CYCLES_CONCURRENT_STATES_FACTOR=0.6 降低并发状态数。
    光子数组 + BDPT 顶点 会再吃一截，OOM 时先降这个再降 photon_capacity。

  10.7 构建树、命令、链接

    独立目录，论坛原话: 换分支不要在同一个
    build_windows_Full_x64_vc17_Release 上硬编。
      E:\build_windows_scycles_x64_vc17_Release

    Windows make.bat 和 Linux make 不是 1:1。
    需要 GPU cubin 时用 make release 那套 flags，或 cmake-gui 勾上
    WITH_CYCLES_CUDA_BINARIES 再编。
    「make」无参数经常不编 GPU 核，启动后才去找 cl.exe。

    链接阶段 Cycles 报一长串 OpenImageIO:
    旧 build 目录引用了过期 lib，删整个 build 树重配。
    装了 vcpkg 的 VS 可能给 Cycles 乱开 VS_GLOBAL_VcpkgEnabled，
    论坛补丁是对 cycles_add_library 关掉它。

    机器内存: 编 CUDA kernel 建议 64GB；16GB 机器开全 arch 会
    cicc 被系统杀掉，表现为 CUDA binaries 编到一半消失、
    WITH_CYCLES_CUDA_BINARIES 被 cmake 悄悄拨回 OFF（#32294，
    常见原因其实是没找到 nvcc，检查 CMakeCache 里 CUDA_NVCC）。

  10.8 日常循环（改 kernel 头文件时）

    1. 改代码
    2. 编 intern/cycles（Release）
    3. 清 %APPDATA%\...\5.3\cache\kernels 和 OptixCache
    4. 从 VS x64 Native Tools 提示符启动 blender（若仍走 JIT 兜底）
    5. 看控制台是否重新 Compiling CUDA/OptiX kernel，有没有
       cuModuleGetGlobal kernel_params 失败（结构体大小变了）

    cuModuleGetGlobal("kernel_params") + cuMemcpyHtoD 失败
    = KernelParamsCUDA host/device 尺寸不一致，正是 7.7-(3)(4)。

13. 风险和预案
--------------

  R1 CUDA 编译器吃不消 shade_volume + BDPT + photon
     预案: 阶段 8 拆 module；或第一期 BDPT 与光子不同时编进 shade
     （用 kernel feature 宏，场景没开 BDPT 就不编进）

  R2 OptiX 上 photon_emit 当普通 CUDA kernel 求交（v1.0 方案写错过）
     症状: 编译 optixTrace 不在 pipeline 内、或运行非法、或永远 miss
     预案: 先 CUDA 软件 BVH 跑通；再给 emit/generate 做 OptiX raygen
     （复用旧 PIP_PHOTON 经验）。gather 留在现有 SHADE module。

  R3 Metal cache-miss 重试在 CUDA 上语义不同，BDPT 对纹理玻璃能量错
     预案: CUDA 上 SR_CACHE_MISS 恒 false；复杂 OSL/纹理场景单独对比 Metal 参考图
     （没有 Mac 就用他仓库的 regression 描述，先保证无纹理玻璃正确）

  R4 室内场景双计或变黑（你 SPPM 踩过的坑）
     预案: 不要把旧 partition/replace 补丁搬回来。
     他的光子图“替换 PT 采不好的那类 transport”，划分在 roughness threshold。
     验收必须含室内浴缸/泳池，能量和纯 PT 4096spp 比，允许偏 5%，不允许大面积黑。

  R5 DLSS 接回去和 SCycles denoiser 调度冲突
     预案: DLSS 只挂视口，F12 仍 OIDN；冲突时保 OIDN，DLSS 可暂时关

  R6 整目录 checkout 丢掉 BIKINI 在 intern/cycles 的其它私货
     预案: 阶段 2 之后立刻
       git log bikini-pre-scycles -- intern/cycles
       列出不在 SPPM/DLSS 里的提交（例如 ddx 若进了 Cycles SVM）
       有则单独 cherry-pick 到 feature/scycles-windows

  R7 SCycles 继续推，你合到一半他 main 又动了
     预案: 锁 pin 在开始时的 scycles SHA（写入本文件顶部）
     功能稳定后再 git fetch 一次，只合 intern/cycles

  R8 HIP/AMD 用户
     预案: 第一期 UI 对 HIP 灰掉光子/BDPT，走官方 PT。不要承诺。

  R9 Windows TDR 砍掉长 kernel
     预案: emit/generate 切片 + 中间 synchronize；视口尤其要切。
     开发可调 TdrDelay，产品不允许。见 7.7-(2)

  R10 KernelParamsCUDA 超过 64KB 常量内存
     预案: sizeof 断言；超了就把光子/BDPT/guiding 指针改成旁路结构。
     见 7.7-(3)

  R11 host/device IntegratorStateGPU 对齐不一致
     症状: 焦散花、radius 乱、crash in gather
     预案: offsetof 对拍、static_assert sizeof。见 7.7-(4)

  R12 开门控时把 GPU Guiding 字段带进 CUDA ShaderData
     症状: 寄存器爆、occupancy 归零、编译超时
     预案: 第一期 CUDA 完全不编 guiding_gpu.h。见 7.7-(5)

  R13 Metal 设备判断导致 Windows 上 alloc 被跳过
     症状: 开关开了、图里没有焦散、指针 null
     预案: if (metal) 改成 GPU transport；launch 前 assert capacity>0

  R14 OSL + OptiX + BDPT
     预案: 第一期 OSL 材质禁用光子/BDPT，UI 提示改 SVM/Principled

  R15 Windows 运行时 JIT 找不到 cl.exe
     预案: 开发期 WITH_CYCLES_CUDA_BINARIES=ON + 只编本机 sm_XX。
     不要把「关 binaries 现场 nvcc」当默认。见第 10.1 节。
     来源: devtalk #27754 #41443，LazyDodo

  R16 OptiX SDK 比驱动新 → "driver too old"
     预案: 锁当前 BIKINI 能用的 SDK 8.x 和现有驱动。见 10.3
     来源: devtalk #44196

  R17 CUDA 13 编 OptiX PTX 失败 / 不认 sm_50
     预案: 用 CUDA 12，或确认 #152789 修复已在树里。见 10.4

  R18 改完 kernel 仍加载旧 cubin；OptixCache 损坏
     预案: 清 cache/kernels 和 %LOCALAPPDATA%\NVIDIA\OptixCache
     来源: #73533、手册 GPU rendering

  R19 OptiX continuation stack too large / INTERNAL_COMPILER_ERROR
     预案: emit/BDPT 不要塞进现有 shade raygen；首测不用 AO/Bevel。
     来源: #150085

  R20 Illegal address / 4090 比 3090 更爱 OOM
     预案: CYCLES_CONCURRENT_STATES_FACTOR=0.6；降光子容量。
     来源: #109025 #98348

15. 每天的最小闭环（避免改一周才知道编不过）
----------------------------------------------

  Day 1: 阶段 0–2，提交 “replace intern/cycles”
  Day 2: DLSS 接回 + WITH_CYCLES_CUDA_BINARIES=ON（只编本机 sm）
         PT-only 能 GPU 出图。不要关 binaries 赌 JIT。
  Day 3: 打开 __SCYCLES_GPU_TRANSPORT__ 的 include，先只编、不 launch
  Day 4: 强制 Cycles 设备=CUDA（关 OptiX），photon_emit launch + 玻璃球
  Day 5: shade_surface gather 写出 Combined，焦散可见（仍是软件 BVH）
  Day 6–7: BDPT light generate + connect，关光子也能出 SDS（仍 CUDA）
  Day 8+: OptiX raygen 接 emit/generate；对比 CUDA 与 OptiX 同一场景
  之后: 体积、位移、光谱、切片防 TDR、拆 module、测试
  GPU Guiding 不进这一轮。

  每个 Day 结束必须有一个能启动的 blender.exe。
  崩了就 git revert 当天，不要在坏构建上叠功能。

19. 给自己的提醒
----------------

  你说“我好像也没改过什么东西”——Cycles 里其实改了 SPPM 和 DLSS 两大块。
  本方案扔掉 SPPM、保住 DLSS，这个边界不要在实施时重新谈判。

  他的焦散不是“加几个文件”，是 IntegratorState + GPU kernel 表 + 调度器
  一起换。Windows 适配的本质是把门控从 Metal 扩到 CUDA，并补上 host launch。
  算法已经在 .h 里，不要重写 photon_mapping.h。
  但 OptiX 求交入口必须当新 pipeline 做，这不是开门控能代替的。
  第一期不要碰 GPU Guiding。那是另一套 Metal 专用 ShaderData 字段。

  对照机（旧 Release）留到第 12 节全部勾完再删。
